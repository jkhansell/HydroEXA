flow (and, in progress, coupled sediment transport) built on
[AMReX](https://amrex-codes.github.io), with a Python companion package for
preprocessing and analysis.

## Measuring the tree

`docs/architecture.md` is generated, never hand-written. It answers the
questions a line count cannot: where the code mass actually sits, and which
files a change can reach.

```bash
uv run pyhydroexa-audit --markdown docs/architecture.md   # regenerate
uv run pyhydroexa-audit --top 5                            # quick look
```

The committed report is measured from a **clean worktree at HEAD**, not from the
working tree, so that uncommitted edits and untracked scratch scripts cannot
inflate the numbers it attributes to a commit:

```bash
git worktree add --detach /tmp/audit-tree/HydroEXA HEAD
uv run pyhydroexa-audit --root /tmp/audit-tree/HydroEXA \
    --markdown docs/architecture.md
git worktree remove /tmp/audit-tree/HydroEXA
```

Which means the report only moves when code is committed: a hand-edited file, or
a plotfile dropped into a test directory, is not part of the measurement until
it is part of the tree.

The metrics are deliberately few and blunt:

- **comment-aware SLOC** — comments and docstrings are counted separately, so
  the comment ratio is meaningful rather than inflated by boilerplate;
- **mass entropy / effective file count** — a Shannon entropy over the per-file
  SLOC distribution. `0.94` normalized and "100 files behave like 60 equal
  ones" says the mass is spread out; a collapse in that number says a few files
  ate the codebase;
- **fan-in / fan-out with instability** — `Ce / (Ca + Ce)`: `0` means "treated
  as public API, change with care", `1` means "depends on everything, breaks
  easily";
- **cycles and condensation depth** — an import cycle defeats incremental
  reasoning, and the depth is how many layers one edit can ripple through.

Findings are ranked by the measurement itself, not by taste, and the thresholds
live in `pyhydroexa/audit/report.py` where they can be argued with.

## Building these docs

```bash
# once, from the repository root (uv only, no conda)
uv sync --group docs

# Doxygen XML (only needed for the C++ API pages)
make -C docs doxygen

# HTML into docs/_build/html
make -C docs html
```

`make -C docs html` runs both steps and drops straight back out if `doxygen`
is not on `PATH`.

On Kabré (where this is developed) the pieces are not in the system image, so:

```bash
module load gcc/13.4.0        # the prebuilt doxygen needs libstdc++ >= 3.4.30
export UV_CACHE_DIR=/data/jovillalobos/uv/.cache   # /data is LFS: faster than NFS
make -C docs html DOXYGEN=/data/jovillalobos/tmp/docs/doxygen-1.18.0/bin/doxygen
```

The build artifacts (`docs/_build/`, `docs/doxygen/xml/`,
`docs/api/generated/`) are gitignored: nothing generated is ever committed.

## Documentation roadmap

Two items were on this list when the tree was scaffolded. The first is done; the
second still moves code around and is still ahead.

1. **Doc-comment every C++ entity** — done. Every file, type, function and
   parameter in `include/` carries a `/** ... */` block, the Doxyfile now sets
   `WARN_IF_UNDOCUMENTED = YES` and `WARN_AS_ERROR = YES`, and both
   `make -C docs html` and CI build with `-W`. A missing comment fails the
   build instead of printing a warning into the log.
   `EXTRACT_ALL` stays on deliberately: it keeps the index structurally
   complete, so a forgotten entity shows up as an empty description in the
   output *and* as an error, rather than as a page that silently does not
   exist. No page in this tree needed editing for the pass, which is the
   property the scaffold was chosen for.
2. **Migrate the case analysis code into `pyhydroexa.analysis`.** The per-case
   scripts (`tests/dambreak/analyze.py`, `metrics_table.py`, `plot.py`,
   `plot_output.py`, …) encode reusable knowledge — length-weighted norms, the
   two uniform yardsticks, `gain_base` / `gain_stable`, the AMR box overlays.
   They belong in the package, with the test directories reduced to inputs plus
   a thin `run.sh`. Because the Python API is generated by walking
   `PyHydroEXA/src/pyhydroexa`, a migrated module is documented the moment it
   lands — no list to update here.

The Python package was already split along the axis those migrations need:
`io/` reads, `analysis/` reduces to numbers, `plotting/` draws. That separation
also removed the one cycle the audit found (`plotfile.py` reached into
`animation.py` through a function-local import); the report in
`architecture.md` is the check that it stays gone.

```{note}
`docs/PIPELINE.md` is the reference for the numerical pipeline (time stepping,
tagging, fluxes, conservation). `docs/doxygen/` holds only configuration; its
`xml/` output is generated.
```
