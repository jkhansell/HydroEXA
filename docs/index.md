# HydroEXA

GPU-accelerated, performance-portable adaptive-mesh solver for shallow water
flow (and, in progress, coupled sediment transport) built on
[AMReX](https://amrex-codes.github.io), with a Python companion package for
preprocessing and analysis.

## What lives where

| Path | Contents |
|---|---|
| `include/`, `src/` | C++ solver: `AmrMeshState` (AMR state machine), `solvers/` (CRTP interface + Roe / HydrostaticRoe), `io/`, `utils/` |
| `PyHydroEXA/src/pyhydroexa` | Python companion package (preprocessing, postprocessing) |
| `docs/` | this documentation tree |
| `tests/` | end-to-end cases; `tests/dambreak/` is the scored SWASHES battery |

## Building these docs

```bash
# once, from the repository root (uv only, no conda)
uv sync --group docs

# Doxygen XML (only needed for the C++ API pages)
make -C docs doxygen

# HTML into docs/_build/html
make -C docs html
```

`make -C docs html` runs both steps and drops straight back out if `doxygen`
is not on `PATH`.

On Kabré (where this is developed) the pieces are not in the system image, so:

```bash
module load gcc/13.4.0        # the prebuilt doxygen needs libstdc++ >= 3.4.30
export UV_CACHE_DIR=/data/jovillalobos/uv/.cache   # /data is LFS: faster than NFS
make -C docs html DOXYGEN=/data/jovillalobos/tmp/docs/doxygen-1.18.0/bin/doxygen
```

The build artifacts (`docs/_build/`, `docs/doxygen/xml/`,
`docs/api/generated/`) are gitignored: nothing generated is ever committed.

## Documentation roadmap

The scaffolding is deliberately layout-agnostic, because the two things that
still have to happen will both move code around:

1. **Doc-comment every C++ entity.** Doxygen currently runs with
   `WARN_IF_UNDOCUMENTED = NO` and `EXTRACT_ALL = YES`, so the API pages show
   the real structure of the solver with little prose. The endpoint is one
   `/** ... */` block per public type, function and parameter, then flipping
   `WARN_IF_UNDOCUMENTED = YES` in `docs/doxygen/Doxyfile` and building with
   `-W` as a gate. No page in this tree needs editing while that happens.
2. **Migrate the analysis code into `pyhydroexa`.** The per-case scripts
   (`tests/dambreak/analyze.py`, `metrics_table.py`, `plot.py`, `plot_output.py`,
   …) encode reusable knowledge — length-weighted norms, the two uniform
   yardsticks, `gain_base` / `gain_stable`, the AMR box overlays. They belong in
   `pyhydroexa.analysis` (and friends), with the test directories reduced to
   inputs plus a thin `run.sh`. Because the Python API is generated by walking
   `PyHydroEXA/src/pyhydroexa`, a migrated module is documented the moment it
   lands — no list to update here.

```{note}
`docs/PIPELINE.md` is the reference for the numerical pipeline (time stepping,
tagging, fluxes, conservation). `docs/doxygen/` holds only configuration; its
`xml/` output is generated.
```
